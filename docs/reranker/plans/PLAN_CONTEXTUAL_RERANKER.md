# 計画：文脈を使うリランカー（Contextual Reranker）

作成: 2026-08-12
前提: `docs/reranker/plans/PLAN_RERANKER.md`（既存の文脈なしリランカー）/ `docs/reranker/reports/PHASE0_RERANK_REPORT.md`
位置づけ: **これまでのリランカーは文脈を一切使っていなかった**（holdout 文脈 0%、train 3.3%）。本計画は「文脈で正解が割れるケースを、文脈を見て当てる」モデルを、**コーパスから作った文脈付きデータ**で学習・評価する。実IMEログには依存しない（作成者1名で偏るため）。

> この文書は**エージェントがそのまま実行できる仕様書**として書く。判断が要る所は既定値を置いた。迷ったら既定値でよい。

---

## 0. なぜやるか（一段落）

Mozc は「読み→表記」の事前分布が強い。AI が Mozc を超えて価値を出せる本丸は **文脈による同音異義の弁別**（`きしゃ`→記者/汽車/貴社 を前の文で決める）。ところが現行データは文脈がほぼ空で、モデルは文脈を学ぶ動機がなく、実質「賢い頻度表」になっていた。**文脈が効くデータを作らない限り、文脈判断は学習も測定もできない。** 本計画はその土台を作る。

---

## 1. 中心仮説と成功の定義

- **仮説**: 文脈付きデータで学習すれば、同音異義（曖昧読み）の hit@1 が「文脈あり」条件で「文脈なし」条件より有意に上がる。
- **主要指標（これが本命）**: 曖昧読みサブセットでの `hit@1(文脈あり) − hit@1(文脈なし)` = **文脈寄与デルタ**。
  - デルタ ≥ +5pt を一次目標（要再設定）。
  - デルタ ≈ 0 なら「まだ文脈を使えていない」＝データ/形式の作り直しが必要、という**失敗検知**になる。
- **副次指標**: 最新ニュース評価で Mozc 超え、退行 < 2%。

---

## 2. データ構築（最重要・具体仕様）

### 2.1 出どころ（コーパス、オフライン）
- 学習・同分布評価用: **日本語 Wikipedia 本文**＋**やや古いニュース**＋（任意）青空文庫。
- 時系列・別文脈評価用: **最新ニュース記事**（学習に一切使わない。トピック・時期が異なるものを別途取得）。
- すべて「自然な文」であること（箇条書き・表・コードは除外）。

### 2.2 抽出パイプライン（1文ごと）
形態素解析で読み付きに分解し、変換単位ごとにレコード化する。

使うツール（既定）:
- 形態素解析＋読み: **SudachiPy（full 辞書、分割モード B）**。読みはカタカナで出るので**ひらがなに正規化**。
- 正規化: **NFKC**、読みは全てひらがな化。
- N-best: **既存の修正済み Mozc N-best 抽出**（フル文節連結・十分な N。segment(0) だけの旧版は使わない）。

各content語（名詞・動詞・形容詞など。助詞・記号・数字のみは除外）について:

| フィールド | 作り方 |
|--|--|
| `reading` | その語の読み（ひらがな正規化） |
| `context_prev` | **その語より前のテキストを、直前の文終端（。！？）で切って"進行中の一文"だけにする**。その上で末尾から最大 50 文字にクリップ。※IMEは変換時に後続を知らないので**前方文脈のみ**（後続は使わない）。**この切り出しは学習生成（`build_ctx_dataset.py`）と推論フックで完全に同一の関数**を使うこと（ズレると学習分布と食い違い、性能が静かに劣化する） |
| `gold` | その語の表記（surface） |
| `mozc_nbest` | `reading` を Mozc に変換して得た候補列（フル表記、十分な N=50〜100） |
| `gold_in_nbest` | `gold` が `mozc_nbest` に含まれるか |
| `source` | `wiki` / `news_old` / `news_fresh` など |
| `doc_id`,`sent_id` | 分割の漏れ防止に使う（文書単位分割のため必須） |

### 2.3 曖昧読みの明示（文脈が効く教材を必ず入れる）
文脈は「同じ読み × 違う文脈 → 違う gold」の対比が無いと学べない。これを**設計で保証する**。

1. 全抽出後、`reading → {gold: 頻度}` の辞書を作る（パス1）。
2. **曖昧読み** = 異なる gold を 2 つ以上持ち、各 gold の頻度 ≥ 5 の読み。
3. 各レコードに付与:
   - `ambiguous`（bool）
   - `reading_gold_count`（その読みの異なり gold 数）
4. **学習データの構成比**: 曖昧読みインスタンスを **30〜40%** 含める（少なすぎると文脈が死ぬ、多すぎると分布が歪む）。残りは非曖昧＝アンカー（頻度表としての土台・忘却防止）。
5. **評価データ**: 各評価セット内に **曖昧サブセット（≥ 500 件）** を必ず確保。ここが主要指標の測定対象。

### 2.4 レコード例
```json
{
  "reading": "きしゃ",
  "context_prev": "朝日新聞の",
  "gold": "記者",
  "mozc_nbest": ["汽車","記者","貴社","기차..."],
  "gold_in_nbest": true,
  "ambiguous": true,
  "reading_gold_count": 3,
  "source": "wiki",
  "doc_id": "wiki_00123",
  "sent_id": "wiki_00123_s07"
}
```

### 2.5 品質フィルタ（gold ノイズ対策）
コーパス由来は gold にノイズが乗る。以下を既定で適用:
- content 語のみ（助詞・記号・URL・絵文字・数字のみ を除外）。
- `reading` 長 1〜16、`gold` 長 1〜12 程度。
- 読みが取れない/未知語は捨てる。
- （任意・推奨）**2つ目の解析器（MeCab+UniDic）と読みが一致する語だけ採用**して精度を上げる。
- **本番実行前に 300 件を手目視監査**し、gold 正解率を記録（目標 ≥ 95%）。ダメならフィルタを締める。

### 2.6 量の目標
| データ | グループ数（目安） | 備考 |
|--|--|--|
| train | 100,000〜300,000 | うち曖昧 30〜40% |
| eval: seen | 2,000 | train から抽出（後述） |
| eval: unseen（同分布） | 2,000〜3,000 | train と別文書 |
| eval: fresh news | 1,000〜2,000 | 最新記事、完全別 |

まず**小さく（train 2万・各eval 1千）パイプラインを通してから**フルスケールへ。

## 3. 分割プロトコル（漏れ厳禁）

あなたの3分割を採用し、漏れ対策を明示する。

- **分割は文書単位（doc_id）**で行う。文・語単位で割ると同一文書の文脈がリークする。
- **train**: Wikipedia＋old news の文書集合 A。
- **eval: seen** … train に**含まれる文書**から別サンプル（記憶・適合の上限を測る診断用）。
- **eval: unseen（同分布）** … A と同じコーパスだが**train に無い文書**（同分布での汎化）。
- **eval: fresh news** … 最新ニュース（時期・話題が別。真の頑健性）。
- 3 セットとも**曖昧サブセットを内包**するよう構成。
- fresh news は train 期間より**後の記事**を選び、固有名詞・話題の重複を極力避ける。

評価の階段: **seen（天井）→ unseen（汎化）→ fresh（頑健性）**。fresh の数字が"本当の実力"。

## 4. 学習トラック（あなたの2通り＋対照）

同じデータ・同じハイパラで、**初期重みだけ変える**（1変数だけ動かす原則）。

| トラック | 初期重み | 目的 |
|--|--|--|
| **A: 素体から** | `cl-nagoya/ruri-v3-pt-70m`（事前学習済みの素） | 文脈付きで新規学習 |
| **B: 現行から継続** | 現行の文脈なし学習済みチェックポイント（`artifacts/rerank/ruri70m_ce` 相当） | 文脈なし学習の上に文脈を足す |
| C: 対照（学習なし） | 現行モデルそのまま | 比較の基準線 |
| baseline | Mozc 単体 | 最下限 |

比較の狙い（あなたの問い）: **「文脈なしで先に学習した事実が、差を開くのか（Bが不利）／プラスになるのか（Bが有利）」** を A vs B で見る。

モデルサイズは **70m を主線**（現行と揃える）。30m は速度が問題になった時の任意の二次実験。

### 4.1 ハイパラ / セットアップ
- 学習スクリプトは既存 `tools/rerank/train_cross_encoder.py` を使う（`build_pair_text` が既に `読み/文脈/候補` を組む）。
- **max_len は 128**（文脈トークンが入るので、配布用の 48 では文脈が切れる。学習・評価とも 128）。
- 損失は現行の pointwise BCE のまま（A/B 比較を汚さないため、まず損失は固定）。listwise 損失は**本実験の後の任意改善**。
- τ（マージン）は**モデルごとに再スイープ**（A と B で別物）。`tools/rerank/margin.py` を使う。
- fp16 AMP・grad-checkpointing は既定 ON。
- 曖昧オーバーサンプリングは §2.3 の構成比で実現（データ側で調整、サンプラは単純 shuffle でよい）。

## 5. 評価プロトコル（文脈の効きを必ず測る）

**全評価セット × 全モデル**で、次を出す:

1. **文脈あり / 文脈なし の両方**で推論（`context_prev` を空にした版も走らせる）。差分が**文脈寄与デルタ**。
2. **曖昧サブセット**を分離集計（ここのデルタが主要指標）。
3. 指標: `hit@1`, `hit@3`, `MRR`, `回復率`(Mozc miss上), `退行率`(Mozc hit上), `gold_in_nbest 率`。
4. すべて**モデル別に選んだ τ** で算出。
5. 出力は機械可読 JSON（`artifacts/rerank_ctx/eval_<model>_<set>.json`）＋要約表（markdown）。

### 5.1 読み取りの決定ルール
- **文脈が効いている条件**: 曖昧サブセットで `hit@1(文脈あり) − hit@1(文脈なし) ≥ +5pt`（seen/unseen 両方で正、fresh でも正なら本物）。
- **A vs B の勝者**: **fresh news の hit@1** が高い方を採用。seen だけで勝っても記憶なので不採用。
- **デルタ ≈ 0 のとき**: 文脈がまだ死んでいる。原因究明（入力形式・context_prev 実データ・max_len・曖昧比率）に戻る。**この失敗検知を必ず回す。**

## 7. エージェント作業手順（この順に実行）

1. **データ抽出器 `build_ctx_dataset.py` を実装**（§2）。SudachiPy＋Mozc N-best＋正規化＋フィルタ。まず 1 文書で動作確認。
2. **曖昧マップ生成**（§2.3）。`reading_gold_map.json` を出す。
3. **小スケール試走**: train 2 万・各 eval 1 千で全パイプラインを通す。
4. **gold 手目視監査 300 件**（§2.5）。正解率 < 95% ならフィルタ調整。
5. **文書単位で 4 分割**（§3）。曖昧サブセットが各セットに ≥500 入っているか確認。
6. **フルスケール抽出**（§2.6）。
7. **Track A 学習**（素体から）。τ スイープ。
8. **Track B 学習**（現行から継続）。τ スイープ。
9. **全モデル×全セットを評価**（§5）。文脈あり/なし・曖昧サブセット込み。
10. **`summary.md` と `docs/reranker/reports/PHASE_CTX_REPORT.md` を作成**。決定ルール（§5.1）で結論（文脈は効いたか／A・B どちら）を明記。

各ステップの成果物 JSON を必ず残すこと。

---

## 8. ガードレール（ハマり・誤結論の防止）

- **1 回に 1 変数だけ動かす**。A/B は初期重み以外（データ・ハイパラ・損失・max_len）を完全に揃える。
- **max_len 128 を学習・評価で統一**（文脈を切らない）。配布用 48 は文脈なしモデルの話なので混同しない。
- **τ はモデルごとに再スイープ**。使い回さない。
- **分割は文書単位**。文/語単位分割は文脈リークで数字が嘘になる。
- **必ず「文脈なし」条件も測る**。文脈ありだけ見ると、頻度表の改善と文脈の改善を区別できない。
- **gold は手目視監査してから本番**。0.0 や崩壊が出たら過去同様まずバグ/正規化を疑う（ひらがな/カタカナ、NFKC、Mozc 側の読み形式）。
- **fresh news は学習に一滴も混ぜない**。時期・話題の重複も避ける。

## 9. 文脈導入の副作用（承知しておく）

- 文脈トークンを読むぶん、**推論は文脈なし版より重くなる**（max_len 48→128）。配布時のレイテンシは再計測が必要。バッチ・候補数上限で吸収する前提。致命的ではないが、"文脈の価値 vs 速度コスト"は最後に天秤にかける。
- 文脈ありが**曖昧サブセットで明確に勝てない**なら、文脈を積むコストに見合わない＝文脈なし版を出荷して本件は保留、という判断もあり得る（§5.1 の失敗検知）。

## 10. 配布時の適応的デグレード（Phase 3・統合時に実装）

低スペック端末でも破綻しないための仕組み。**本実験（オフライン学習）には不要**だが、統合時の設計として確定しておく。

### 10.1 二層構成
- **層1: 毎回のハードタイムアウト（絶対にユーザを待たせない）。** 変換 1 回ごとに締切（既定 **200ms**）を張り、超えたら**その回は Mozc の並びをそのまま返す**。リランクが遅れても IME はブロックしない安全弁。
- **層2: 傾向で段階ダウン。** **5 回連続で締切超過**したら恒久的にティアを 1 段下げる。速くなったら 1 段戻す（ヒステリシスでばたつき防止）。

### 10.2 デグレード階段（軽い順）
1. **cand_cap を下げる**（30→15）。**溢れた候補は捨てず、Mozc の元順のまま後ろに連結**（リランク済みが前、残りが後ろ）。Mozc top-1 は τ で保護。
2. **文脈を短く**（50→20 字）。
3. **文脈を空＋max_len 最小（同一 70m モデルのまま）**。入力が `読み [SEP] 候補` だけになり max_len 24〜32 で大幅高速化。**30m へ切り替える前に、まずこの"同一モデル文脈空"モードを試す**（モデルを 2 個持たずに済む）。
4. 上で足りない/品質が崩れる時のみ、**30m へ切替**（同梱していれば）or 次へ。
5. **最終フォールバック = Mozc 単体**（リランク無効）。どんな端末でも最低限 Mozc として動く。

### 10.3 「同一モデル文脈空」ティアの採否は §5 の結果に紐づく
ステップ 3 が成立するか＝「文脈ありで学習したモデルが、文脈を抜いても実用的に動くか」は、**§5 の文脈あり/なし評価がそのまま答えを出す**。
- 文脈なし hit@1 が現行の文脈なしモデル並みに保たれる → **ステップ 3 を採用、30m 不要（同梱 1 モデルで完結）**。
- 文脈なしで崩れる → ステップ 3 を飛ばし 30m or Mozc 単体へ。

学習データはアンカー（文脈が薄い/無い例）を 60〜70% 含むため、文脈なしモードが生き残る公算は高いが、**断定は評価待ち**。

### 10.4 補強（任意）
- 起動時に一度だけ**軽いベンチ**を走らせ、端末性能で初期ティアを選ぶ（層2 の反応式と併用し、初回のもたつきを減らす）。
- 注意: 文脈を削るとこの"文脈モデル"の本体価値（同音異義の弁別）は失われ、頻度表相当に戻る。これは低スペック向けの割り切りであり、品質の下限は常に Mozc。

## 11. 一行サマリ

> これまでのリランカーは文脈ゼロで学習・評価していた。本計画は**コーパスから「同じ読みが文脈で割れる」文脈付きデータを作り**、素体から(A)／現行から継続(B) の 2 通りで学習し、**seen / unseen / 最新ニュース**の 3 段階＋**文脈あり/なし**で測る。主要指標は**曖昧読みでの文脈寄与デルタ**。デルタが立てば「文脈で賢いIME」が初めて実証できる。立たなければ即座に失敗検知して原因に戻る。
