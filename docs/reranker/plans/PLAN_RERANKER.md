# Mozc-Ai 次期計画：Mozc N-best リランカー

作成: 2026-08-11
前提メモ: `docs/background/STATUS_FOR_PLANNING.md`
位置づけ: 「PLaMo LoRA 自由生成」から方針転換するための具体計画。何を・どのモデルで・どれだけのデータで・どう評価するかを決める。

---

## 0. 一言で

**PLaMo による自由生成 IME をやめ、「Mozc が出した候補を並べ替える／少数だけ追加する」小型クロスエンコーダ・リランカーに絞る。**
ベースは日本語ネイティブの ModernBERT-Ja 系（30〜130M）。CPU int8 で 1 変換あたり数十 ms を狙えるため、現状の「CPU 推論 291 秒/回で実用外」という最大の壁が構造的に消える。

---

## 1. なぜ方針転換するか（現状データの含意）

STATUS_FOR_PLANNING の数字が示していること:

1. **自由生成フル IME は筋が悪い。** CPU で約 291 秒/回、崩れ入力はエコーバック（`をきる`→`をきる`、`とうきょうとと`→`東京都都`）。1B 生成モデルに変換エンジンそのものをやらせている限界で、モデルを大きくしても遅延は悪化するだけ。
2. **評価が意思決定に使えない。** v1/holdout が学習データからの抜き出しで、Mozc 既存候補も空にしがち。「Mozc に対してどれだけ改善したか」を一度も測れていない。
3. **一番の資産は「Mozc が落とすケース」＝残差。** Mozc の辞書変換は非常に強い。AI が価値を出せるのは Mozc が 1 位を外す場面だけ。ここに全リソースを寄せるのが合理的。

リランカーはこの 3 点を全部回避する:

| 課題（生成方式） | リランカー方式での解 |
|--|--|
| CPU 291 秒/回 | 候補スコアリングのみ → CPU int8 で数十 ms/変換 |
| 崩れ入力でエコーバック/破綻 | 生成しない。Mozc 候補集合の外は出さない（＝破綻不能） |
| 複数候補生成が弱い（単一候補化） | 並べ替えなので N-best がそのまま複数候補になる |
| Mozc 比の改善が測れない | 評価軸が「Mozc top-1 を超えるか」に一本化される |

## 2. モデル選定

### 2.1 役割の定義

- **入力（query 側）**: 読み ＋ 文脈（直前の確定文字列など）。例: `現在の入力: とうきょうと / 直前: 私は`
- **入力（candidate 側）**: Mozc が返した変換候補 1 つ。例: `東京都`
- **出力**: その候補の「文脈適合スコア」（sigmoid 0〜1）。
- **使い方**: Mozc の N-best を全候補スコアリング → 並べ替え。Mozc 自身のスコアと線形ブレンドも可（`α·mozc + (1−α)·reranker`）。

### 2.1.1 レイテンシ設計（重要）

クロスエンコーダは **候補数ぶん推論が走る**（10 候補なら 10 回）。Windows CPU では 1 変換で 50 ms をすぐ超え得るため、速度は最初から設計に織り込む。以下を Phase 1 の選択肢として残す:

- **バッチ推論**: N-best をまとめて 1 バッチで流す（逐次より大幅に速い。まずこれ）。
- **上位 K だけリランク**: Mozc スコア上位 K（例 K=5）だけをスコアリング対象にし、残りは Mozc 順のまま。候補数を固定上限に抑える。
- **二段構え（bi-encoder 一次絞り → cross-encoder 精査）**: 候補が多い時のみ、軽い bi-encoder で粗選別してからクロスエンコーダにかける。必要になったら導入。

実測 p95 を見て、まずバッチ、足りなければ上位 K、それでも足りなければ二段構え、の順で適用する。

これは RAG のリランカーと同じ **クロスエンコーダ**（query と candidate を 1 本に連結して 1 スコア）。IME 版は「読み → 表記」なので語彙的性質は違うが、アーキテクチャはそのまま使える。

### 2.2 ベースモデル候補（すべて日本語ネイティブ・MIT/Apache・ROCm 素直）

ModernBERT-Ja 系（`sbintuitions/modernbert-ja-*`）とその埋め込み事前学習版 `cl-nagoya/ruri-v3-pt-*` が土台。既存の日本語リランカー（hotchpotch 系 v2）もこの上に載っている。

| ベース | パラメータ | 用途 | 備考 |
|--|--|--|--|
| `sbintuitions/modernbert-ja-30m` / `ruri-v3-pt-30m` | 約 37M | **オンデバイス配布ターゲット（速度が足りない場合）** | **fp32 ONNX** で CPU 実用。tiny/xsmall-v2 の土台。※ int8 PTQ はこのタスクで順位が崩壊するため不採用（§4.4 参照） |
| `sbintuitions/modernbert-ja-70m` / `ruri-v3-pt-70m` | 約 70M | **主実験ベース（推奨）** | 品質と速度のバランス。small-v2 の土台 |
| `sbintuitions/modernbert-ja-130m` / `ruri-v3-pt-130m` | 約 130M | 品質上限の実験 | GPU 前提。天井確認用 |

**学習の出発点は 2 通り試す:**

- (A) **素の ModernBERT-Ja / ruri-pt からファインチューン**（本命）。読み→表記という IME 特有タスクを、事前学習の日本語知識の上に新規学習。
- (B) **既存日本語リランカー（`hotchpotch/japanese-reranker-small-v2` 等）から継続学習**（ドメイン適応）。RAG 用重みが転移するか安めのコストで確認。

まず (A) の 70m を主線、(B) を比較として 1 本回す。

### 2.3 なぜ ModernBERT-Ja 系が今回の環境に効くか

- **PLaMo の ROCm 地獄が消える**: Mamba/SSM 非依存の普通の Transformer エンコーダ。`causal_conv1d` / `mamba_ssm` の stub/patch が不要。ROCm/WSL でも素直に回る＝現状の最大の不安定要因が消える。
- **CPU で実用速度**: 70m・fp32 ONNX・バッチ推論で **CPU p50 91ms / p95 300ms**（Windows 実測、フル精度）。PLaMo の 291 秒から約 4 桁改善。
- **配布が軽い**: ONNX（fp32）で実 IME 組み込みが現実的。

> 重要な更新: 当初は int8 ONNX 配布を想定していたが、**post-training int8 量子化はこのモデルでスコア順位が崩壊**（PT↔int8 の Spearman 0.42〜0.84、std が潰れ、Mozc 素と同着まで劣化）。**配布形態は fp32 ONNX** に確定。さらに速度が要るなら int8 ではなく **30m への縮小（fp32）** で対応する。詳細は §4.4。

### 2.4 PLaMo の残す役割

捨てるのではなく **オフラインの teacher / 候補生成器** に降格:

- 「正解が Mozc N-best に無い（＝並べ替えでは救えない）」ケース用に、**追加候補を生成**して学習データを厚くする。
- 将来の蒸留（候補3）で teacher に使う。
- リアルタイム経路からは外す。

## 3. データ計画（ここが成否を分ける）

### 3.1 1 レコードの形

```json
{
  "reading": "とうきょうと",
  "context_prev": "私は",
  "mozc_nbest": ["東京都", "東京と", "とうきょうと", "東京斗"],
  "gold": "東京都",
  "gold_in_nbest": true,
  "source": "residual_wiki"
}
```

学習時はこれを (query, candidate) ペアに展開し、gold=正例 / 他の N-best=**ハードネガティブ**にする。**Mozc の誤変換候補がそのまま最良のハードネガティブになる**のがこの設計の美点。

### 3.2 何のデータを集めるか（種類と比率）

| 種別 | 内容 | 目的 | 目標比率 |
|--|--|--|--|
| **残差（Mozc miss）** | Mozc top-1 ≠ gold のケース | 価値の源泉。リランカーが直す対象 | 40〜50% |
| **成功アンカー（Mozc hit）** | Mozc top-1 = gold のケース | 「正しいものを壊さない」学習。**破滅的忘却の防止** | 35〜45% |
| **崩れ入力** | タイポ/未確定/記号混じり（`をきる`等） | 破綻せず無難に振る舞う | 10〜15% |
| **候補追加ケース** | gold が N-best 外（PLaMo/辞書で補完） | 並べ替えを超える上積み（Phase 2〜） | 5〜10% |

比率のキモは **アンカー**。残差ばかりで学習すると Mozc が既に正しいケースを壊す（regression）。必ず成功例を混ぜる。

### 3.3 どこから作るか

1. **既存 accept レビューの再加工（Phase 1 の主軸）**: 既存 11,128 行は gold の品質が既にレビュー済みで信頼できる。現状プロンプトは Mozc 候補を持っていないので、各 reading を **Mozc に通して N-best を再取得** し、gold と突合してレコード化する。Phase 1 はまずここだけで回す。
2. **残差マイニング（Phase 2 の量産源）**: 日本語コーパス（Wikipedia 本文、ニュース、青空文庫、一般文コーパス等）を形態素解析で「読み↔表記」ペア化 → Mozc に読みを投げ、top-1 が gold と食い違う箇所を収集。
   - **注意**: 形態素解析→読み→Mozc 比較は gold にノイズが乗りやすい（読み付与ミス・表記ゆれ・複合語境界）。**量産は Phase 2 に回し、Phase 1 では主軸にしない。** Phase 2 導入時はサンプリング目視・簡易フィルタ（頻度/長さ/文字種）で gold 品質を検証してから投入する。
3. **実 IME ログ（あれば最良）**: 実際の変換・確定ログがあれば真の分布。無ければ Phase 3 で少量でも収集する仕組みを入れる。

### 3.4 どれだけ必要か（量）

クロスエンコーダのファインチューンは、数万グループ規模から十分効く。1 reading ≒ 5〜20 ペア。

| フェーズ | reading グループ数 | 展開ペア数（目安） | 主眼 |
|--|--|--|--|
| **Phase 1（実証）** | 5,000〜10,000 | 5 万〜15 万 | 「Mozc top-1 を超える」を最短で示す |
| **Phase 2（品質）** | 30,000〜100,000 | 30 万〜150 万 | 残差重点＋アンカー＋崩れ入力で底上げ |

Phase 1 は**既存 11,128 行（accept レビュー）の再加工のみ**で 5k〜10k グループに到達可能（コーパス残差マイニングは使わない）。Phase 2 でコーパス残差を本格投入して量を伸ばす。**「辞書を全部叩き込む」路線は採らない**（暗記機械化しやすく汎化しない。辞書は候補源/制約に留める）。

> **Phase 0 実測**（`docs/reranker/reports/PHASE0_RERANK_REPORT.md`）: 旧 `mozc_batch`（segment(0) のみ）では `gold_in_nbest=0`。  
> **Phase 0.5**（`docs/reranker/reports/PHASE0_5_GATE_REPORT.md`）: フルパス抽出修正後は `gold_in_nbest=0.553` / `not_top1=0.225` → **ゲート GO**（GPU 学習許可）。まだ train は未起動。

## 4. 評価設計（モデルより先に作る）

現状最大のボトルネック。**モデルをいじる前に「本物の holdout ＋ Mozc ベースライン」を用意する。**

### 4.1 真の holdout

- 学習に一切現れない**文単位**で分離（reading 単位分離だと文脈がリークする）。
- 各サンプルに Mozc N-best と gold を付与。
- 残差サブセット（Mozc miss）と成功サブセット（Mozc hit）を**別々に集計できる**よう分割保持。

### 4.2 指標

| 指標 | 意味 | なぜ見るか |
|--|--|--|
| **hit@1（Mozc 単体）** | ベースライン | これを超えられなければ意味がない |
| **hit@1（リランク後）** | 主指標 | Mozc からの純改善 |
| **hit@3 / MRR** | 候補群の質 | 複数候補 UX |
| **回復率**（miss サブセット上） | Mozc が外した中で直せた割合 | 上積みの実力 |
| **退行率**（hit サブセット上） | Mozc が正しいのに壊した割合 | **安全性。ここが高いと不採用** |
| **p50 / p95 レイテンシ（CPU ONNX fp32）** | 実 IME 体感 | 実用可否の関門 |

### 4.3 合格ライン（Phase 0/1 の実測を反映して更新）

- hit@1: **Mozc 比 +13.4pt を達成済み**（31.2% → 44.6%, τ=2.0）
- 退行率: **< 2%** → **1.15% で達成済み**
- レイテンシ: 当初 int8 で <50ms を想定 → **int8 不可のため fp32 で再設定**。速度ワークストリーム後（静か再計測）**p50 ≈42ms / p95 ≈79ms**（旧 91/300。`max_len=48` + ORT intra=12 + **cand_cap=30**）。目標 p50≤50 / p95≤120 達成。詳細は §4.5 / `docs/reranker/reports/PHASE0_RERANK_REPORT.md`。

### 4.4 実測結果スナップショット（2026-08-11、速度更新 2026-08-12）

| 項目 | 値 |
|--|--|
| Mozc 単体 hit@1（holdout 1669） | 31.2% |
| リランク後 hit@1（fp32, τ=2.0, 全候補） | **44.6%（+13.4pt）** |
| gold∈N-best 時 hit@1 | 79.2% |
| 回復率（Mozc miss） | 25.2% |
| 退行率（Mozc hit） | **1.15%** |
| 配布構成 | **ONNX fp32・batch・topK なし・cand_cap=30・max_len=48・τ=2.0** |
| CPU レイテンシ | **p50 ≈42ms / p95 ≈79ms**（旧 91/300。静か再計測 5×250 中央値） |

確定した知見:
- **int8 PTQ は不採用**（順位崩壊。QAT 無しでは回復不能）。配布は fp32 ONNX。
- **topK は不採用**（回復対象の gold は Mozc 下位に多く、K=5 で 39%・K=16 で 95% しかカバーできず精度を削る）。
- **候補数上限 cap=30** は topK とは別物（Mozc top1 を残し、hit 不変で p95 を切る。候補数↔ms 相関 0.90）。
- **バッチ推論が最大の勝ち**（精度ゼロ劣化で逐次比 大幅高速化）。
- **τ はバックエンドごとに別物**（fp32 の τ を int8 に流用してはいけない）。

### 4.5 速度ワークストリーム（完了・品質中立優先）

実施結果（`docs/reranker/tasks/NEXT_TASK_LATENCY.md`）:
1. **トークン長**: p99≈36 / max=46 → 配布 `max_len=48`（100% カバー。動的パディングのため短縮単体の速度差は小さい）。
2. **ORT**: intra=CPU数・inter=1・`ORT_ENABLE_ALL`・**OMP_NUM_THREADS=1**（二重化回避）。
3. **p95**: 主因は候補数。cap=30 で p95≈79ms（目標≤120 達成。cap 無しでも ≈90ms）。
4. **30m**: **不要。** 静か再計測で p50/p95 とも目標達成。

**Phase 2 へ進んでよい。** 詳細数値は `docs/reranker/reports/PHASE0_RERANK_REPORT.md` 速度節。

## 5. 実行環境

| 項目 | 方針 |
|--|--|
| 学習 | **ローカル ROCm 継続で OK。** 30〜130M の普通の Transformer は RX 7800 XT で軽く回り、PLaMo のような Mamba/SSM 由来の不安定さが無い |
| 推論・配布 | **ONNX fp32（CPU）**。オンデバイス IME 組み込みを狙う（int8 は順位崩壊のため不採用、§4.4）。速度が足りなければ 30m fp32 |
| クラウド GPU | **Phase 2 規模学習は Colab を使う。** 手順: `docs/guides/COLAB_TRAIN_GUIDE.md` / ノート `docs/guides/COLAB_PHASE2_TRAIN.ipynb` / タスク `docs/reranker/tasks/NEXT_TASK_PHASE2.md`。**torch は Colab 既設のまま（pip しない）**。ローカル ROCm との dual も可 |

PLaMo で必要だった watchdog/増分再開の重装備は、この規模なら基本不要になる見込み。

### 5.1 既存 IME 統合との接続

現状の `ai_rewriter` は生成/API 呼び出し寄りで、リランカー方式とは接続点が異なる。**Phase 0 の段階で「どこで Mozc の N-best を受け取り、どこで並べ替えて返すか」を 1 経路に明示する。**

想定フロー（設計イメージ）:

```
Mozc 変換 → N-best 取得 → [ここに rerank フック] → スコアで並べ替え → 候補ウィンドウへ返却
```

- 変換確定前の候補リスト（Mozc の segment / candidate list）を rerank フックに渡し、reranker スコアで並べ替えた候補列を返す形にする。
- `ai_rewriter` の「生成して書き換える」経路は残しつつ、新設の「候補を並べ替える」経路を分けるか、rerank に置き換えるかを Phase 0 で決める。
- まずは IME 本体に組み込む前に、**オフラインで N-best を JSON 入出力する rerank スクリプト**として実装し（評価ハーネスと共通化）、統合は Phase 3 で行う。

### 5.2 候補ソーシング（gold ∉ N-best 対策）— Phase 2/3 の新規ワークストリーム

リランクは並べ替えなので、**正解が Mozc の N-best に無いケース（マンション名・稀な固有名詞など）は原理的に救えない**。これは「並べ替え」ではなく「候補を足す」別問題として切り分ける。

- **A: gold ∈ N-best だが順位が低い** → リランカーの仕事（達成済み）
- **B: gold ∉ N-best** → **候補ソーシング**の問題。以下で対応。

方針（優先順）:

1. **ローカル同梱辞書からの候補注入（本命）。** サーバ DB ではなく端末同梱の reading→surfaces マップ（将来 trie/FST 可）。理由: 変換ごとのネットワーク往復は速度・オフライン・プライバシーの全てで NG。「無料維持」条件がそのままローカル化を後押しする。
   - データ源: NEologd（固有名詞・新語の既製辞書、最短の近道）、Wikipedia/Wikidata（よみがな＋ページビューを頻度に）、郵便番号データ／国土数値情報（地名・駅名・施設名）。※ライセンスは配布前に要確認。
   - 頻度で事前ランク付けし、要求時にページ単位で遅延読み込み。
   - **Mozc 既存辞書と diff して、Mozc が既に出せる語は捨てる**（容量を最小化＝無料維持の肝）。
2. **注入と採点の分業。** 引いた候補は**リストの後ろに付ける**（前に差し込まない）。未検証のうちは通常より**厳しい τ**を課し、文脈的に強い一致だけ前へ。Mozc ネイティブ候補の τ（現状 2.5）は据え置き（標準変換を壊さない）。
3. **選択による昇格＋学習フライホイール。** ユーザが 1 回でも選んだ語はユーザ辞書へ昇格 → Mozc が候補化＆学習で押し上げ、τ が守る。さらに**選択ログはリランカー再学習のラベル**になる（個人適応とモデル改善の両取り）。

**着手前のゲート**: holdout の miss を A/B に分け、**B の比率と gold の種類（地名/人名/施設/建物/一般）を測る**。B が多ければ辞書投資の価値大、少なければ後回し。生成（PLaMo）は B の追加候補を**オフラインで作る裏方**に限定し、リアルタイム経路には入れない。

## 6. ロードマップ

**Phase 0 — 土台（最優先, 1〜2 週）**
Mozc から N-best を取り出すパイプライン構築 → 真の holdout 作成 → **Mozc 単体 hit@1 ベースライン測定**（合格ラインはこの数字を見て確定）→ 既存 `ai_rewriter` を読み、rerank フックの接続点（N-best を受けて並べ替える経路）を 1 段落で明示。これが全ての基準点。  
**完了（2026-08-11）**: accept 再加工・split・ベースライン・フック文書まで実施。結果 `gold_in_nbest=0` のため **Phase 1 学習には進まず**、N-best 抽出修正が次タスク（詳細は `docs/reranker/reports/PHASE0_RERANK_REPORT.md`）。

**Phase 1 — 実証（ほぼ完了, 2026-08-11）**
既存 accept レビューを Mozc N-best 付きに再加工（N-best 抽出のフル表記バグを修正）→ ruri-v3-pt-70m からクロスエンコーダ学習 → holdout でベースライン超えを確認。
**結果**: Mozc 31.2% → **44.6%（+13.4pt）／退行 1.15%（τ=2.0）**。バッチ推論＋ONNX fp32。int8・topK は不採用。§4.5 速度短縮完了後 **p50≈42 / p95≈79**（cand_cap=30、静か再計測）。**核心の仮説は実証済み。30m は不要。**
詳細: `docs/reranker/reports/PHASE0_RERANK_REPORT.md` / `docs/reranker/tasks/NEXT_TASK_LATENCY.md`。

**Phase 2 — 品質・候補ソーシング（3〜4 週）**
2 本を並行（速度は §4.5 で実質完了）:
1. **品質**: コーパス残差を本格投入し 30k〜100k グループへ。アンカー比率・崩れ入力を調整。退行率 <2% を保ちつつ hit@1 と gold∈N-best 時精度（現 79.2%）を伸ばす。**τ はバックエンド別に管理**。
2. **候補ソーシング（§5.2）**: B ゲート GO → Mozc-diff 同梱辞書パス構築済み（`artifacts/dict/production`）。リーク制御では一般化リフト≈0 → **追加ソース / 実ログ**が次。**CE データ scale-up は pause**（辞書が主レバー）。
（任意）p50 に余裕が欲しければ 30m fp32 再学習。int8 化はしない。

**Phase 3 — 統合・実ログ（現行メイン）**
Mozc の候補再スコアリング経路に組み込み（オフライン `tools/rerank/phase3_hook.py` → C++ `RerankRewriter` stub）。**選択ログ収集**で正直 B / 辞書ターゲットを作り直す。§5.2 辞書注入は実ログ上の固有名詞需要が確認できてから（accept-holdout 研磨はしない）。詳細 `docs/reranker/tasks/NEXT_TASK_PHASE3.md`。

**Phase 4 — 蒸留/上積み（任意, 将来）**
70m の品質を 30m student に蒸留して速度と精度を両取り（int8 が使えないぶん、モデル縮小がレイテンシの主レバー）。PLaMo は B（N-best 外）の追加候補を**オフライン生成**する teacher に限定。必要ならクラウド GPU をここで検討。

## 8. この計画の一行サマリ

> 生成をやめ、**Mozc が落とすケースに特化した小型クロスエンコーダ・リランカー（ruri-v3-pt-70m, CPU ONNX fp32）** に絞る方針は実証済み: **Mozc 31.2% → 44.6%（+13.4pt）／退行 1.15%／CPU p50 91ms**。
